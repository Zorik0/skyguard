# SkyGuard

**Intelligent operations and data-quality platform for Automatic Weather Station networks.**

**[Live demo →](https://skyguard-zorikos-projects.vercel.app)**

A weather station reports 61.4 °C. Is the region on fire, or is the probe broken?

SkyGuard answers that question, shows its working, estimates what the true value
probably was, and tells the operator what to do about it — without ever
overwriting the original measurement.

```
DETECT  →  EXPLAIN  →  CORRECT  →  ACT
```

---

## The contrast the whole product is built around

Two things happen in the demo network at the same time. Telling them apart is
the entire job:

| | **AWS-007 · Marion Ridge** | **AWS-033 · Newport Headland** |
|---|---|---|
| What happened | Temperature jumps to ~61 °C in one minute | Temperature falls ~7 °C over 40 minutes |
| Humidity | Unchanged | Rises as the air moistens |
| Pressure | Unchanged | Digs a trough, then recovers |
| Neighbours | Nothing, anywhere in the network | The same signature, in geographic order |
| Rate of change | Violates the configured physical limit | Fast, but physically achievable |
| **Verdict** | **Likely sensor fault — 98%** | **Likely genuine weather event** |
| **Action** | Corrected value published, maintenance task raised | Nothing. Data published as measured. |

Both are anomalies. Only one is a problem with the hardware, and only one gets
corrected. A platform that treats them the same is worse than useless — it
either erases real weather or ships broken data.

## Real data vs simulated data

This distinction is enforced throughout the interface, because getting it wrong
would make the whole thing dishonest.

**Live, from real public APIs**

- [Open-Meteo](https://open-meteo.com) — current conditions, hourly forecast,
  grid elevation and ensemble spread. All twelve stations are fetched in a
  single request. No API key.
- [RainViewer](https://www.rainviewer.com) — precipitation radar frames and
  animation.

**Simulated, and labelled `SIMULATED` everywhere it appears**

Public weather APIs cannot tell you the battery voltage of a station that does
not exist. Everything about the fictional hardware — sensor readings, battery,
solar, packet loss, firmware, calibration history, faults — is generated by a
deterministic simulator.

Every value on screen carries a provenance badge: `LIVE`, `SIMULATED`,
`EXTERNAL`, `MODELLED`, `CORRECTED` or `ESTIMATED`. Hovering explains what it
means and where the number came from.

### When the providers are down

The dashboard does not blank, and it does not fall back to silently made-up
numbers. It says *"External weather context unavailable — using simulation
context"* and carries on: detection, classification and corrections all run on
station telemetry, physics rules and neighbour comparison, none of which need
the network. Radar reports itself unavailable rather than showing stale or
invented frames.

## How it decides

### 1. Detection

A deterministic scan over each channel, with every threshold stated and
configurable: sudden spike and drop (z-score against a 90-minute trailing
baseline), rate-of-change violations, frozen channels, variance step changes,
sustained drift, range violations, missing packets, communications degradation,
battery decline and overdue calibration.

There is no black box. The score that comes out is a weighted sum of named
tests, and the tests travel with it into the UI.

### 2. Physics validation

Transparent atmospheric consistency rules — rate limits per channel, absolute
ranges (pressure compared at mean sea level so elevation is not penalised), the
dew-point relationship, cross-sensor coherence, neighbour agreement and
digital-twin agreement. Each rule reports **what it observed** and **the limit
it compared against**, whether or not it fired.

### 3. Weather or hardware?

The central judgement. Evidence is accumulated on both sides with explicit
weights:

- **Toward hardware** — impossible rate of change, other channels flat, no
  neighbour agrees, twin disagreement, frozen channel, out-of-range value.
- **Toward weather** — the same signature appearing at neighbouring stations at
  a plausible lag *and in geographic order*, every channel moving together, the
  twin tracking the station, a rate that is fast but achievable.

Confidence is simply the winning side's share of total evidence weight, so it
can always be explained by listing the evidence — and it can never reach
certainty. When the evidence is genuinely balanced, the verdict is
*indeterminate*, not a coin flip.

Two findings are dispositive and short-circuit the weighing entirely: a channel
with **zero variance** and a value **outside what the instrument can physically
produce** are not measuring the atmosphere at all.

### 4. Corrected values

For probable hardware faults, five independent estimators are combined:

| Source | Weight | What it is |
|---|---|---|
| Physics model | 40% | Last trustworthy reading carried forward along the twin's tendency |
| ML estimate | 30% | Least-squares regression of this station against its neighbour consensus, fitted on the three hours *before* the fault |
| Neighbouring stations | 20% | Relevance-weighted consensus, brought into this station's frame |
| External weather model | 8% | Open-Meteo, elevation-corrected |
| Recent sensor history | 2% | Trailing median before the episode |

Weights are renormalised across whichever estimators were actually available, so
a missing external model widens the prediction interval rather than quietly
biasing the answer. The interval comes from how much the estimators disagree,
floored by the channel's own measurement uncertainty.

**The raw value is never overwritten.** A correction is an additional record
carrying its own method, weights, interval, confidence and model version. The
raw-data export contains the original readings, faults included.

### 5. Neighbour intelligence

Proximity alone is a poor guide — a valley station 8 km from an alpine one is a
bad reference, while two valley stations 60 km apart track each other closely.
Relevance blends distance, elevation difference, terrain character and the
historical correlation of expected conditions.

Values are brought into the target's frame before comparison: temperature by
lapse rate, pressure via mean sea level, and humidity by carrying the
neighbour's **dew point** across and re-expressing it at the target's
temperature — relative humidity is not comparable between sites at different
temperatures.

### 6. Correlation

Twenty anomalies caused by one front are one incident, not twenty. Meteorological
findings cluster across the whole network; hardware findings cluster per station.
Alerts, notifications and reports all work from the incident.

## The simulation

Nothing calls `Math.random()`. Every value is a pure function of a string seed
and a timestamp, so a demo looks identical on every machine and nothing changes
between React renders.

The engine is two stages:

1. **A regional atmosphere.** Every station samples the *same* field, adjusted
   for elevation (lapse rate), terrain and distance from the ocean. Humidity is
   modelled as a dew-point *depression*, which keeps it physically sane across a
   1400 m elevation range. Meteorological events perturb this stage, so they
   appear coherently at every affected station — which is exactly what makes
   them distinguishable from hardware faults.

2. **Imperfect hardware.** Faults are applied here only. A spike at one station
   leaves the regional field untouched, so every neighbour disagrees with it.

Fronts propagate geometrically: arrival time is a projection of each station
onto the direction of travel, at a real frontal speed. The twelve stations sit
on a coherent west-to-east transect of the Pacific Northwest — coast, Coast
Range, Willamette Valley, Cascades, high desert — spanning 8 m to 1450 m, so
elevation physics and neighbour analysis both mean something.

Injectable scenarios: temperature spike, humidity drift, frozen sensor,
excessive noise, battery failure, communications outage, cold front, heat wave,
pressure drop, rainfall event.

## Architecture

One pure function turns `(seed, events, clock)` into the entire application
state — telemetry, anomalies, incidents, alerts, health, maintenance, audit
trail. Every screen reads from that one object, which is what guarantees no two
screens can disagree. Inject a fault at AWS-007 and it appears on the overview,
the map, the health matrix, the alert list, the maintenance queue and the audit
log in the same render.

```
src/
  types/                 Domain model
  lib/
    rng.ts               Seeded PRNG, value noise, fBm
    utils.ts             Maths, dew point, pressure reduction, great-circle
    units.ts             SI everywhere; conversion only at display time
    simulation/          Station network, regional field, faults, scenarios
    physics/             Configurable atmospheric consistency rules
    anomaly/             Detectors, classifier, plain-language narrative
    corrections/         Weighted ensemble, prediction intervals, shadow model
    health/              Per-sensor scoring, predictive maintenance
    incidents/           Correlation, alerts, audit trail, failure signatures
    neighbours.ts        Relevance scoring, consensus, propagation matching
    weather/             Provider interface + Open-Meteo and RainViewer
    models/              Detector comparison and shadow evaluation
    reports/             Client-side CSV and JSON export
    world.ts             Composes all of the above into one state object
  store/                 Zustand: simulation inputs and operator decisions only
  hooks/                 World derivation and memoisation, external context
  components/            charts · map · stations · anomalies · layout · ui
  app/                   15 sections, station and sensor pages, Mission Control
```

The store holds **inputs and operator decisions**, never derived data.
Acknowledgements and incident statuses survive a clock tick; everything else is
recomputed. A full rebuild — 24 hours of minute-resolution telemetry for twelve
stations plus the entire detection pipeline — takes about 200 ms and is
memoised against the exact inputs that produced it.

## Sections

**Monitor** — Overview, Network Map, Live Monitoring
**Investigate** — Anomalies, Incidents, Weather Events, Corrected Values, Historical
**Act** — Sensor Health, Maintenance, Alerts
**System** — Model Lab, Reports, Audit Log, Settings

Plus per-station and per-sensor pages, and a **Mission Control** mode for a wall
display.

Press <kbd>⌘K</kbd> for the command palette and global search, digits and
letters to jump between sections, <kbd>M</kbd> for Mission Control.

### A note on the Model Lab

Precision and recall there are measured against ground truth that exists *only
because this network is simulated* — the exact minutes a fault was injected.
Real hardware never comes with that label. That is precisely why the production
path publishes evidence and rules rather than a score alone.

### A note on the assistant

The operator assistant answers from application state using keyword intents and
explanation templates. It is deliberately **not** a language model and does not
pretend to be one: every answer is assembled from the same objects the screens
render, so it cannot contradict them or invent a number. It sits behind a
provider interface so a real model can be added later — as an additional
provider, not as a replacement for that guarantee.

## Accessibility

Semantic HTML and landmarks, visible keyboard focus, a skip link, keyboard-

in-app preference. Interface density is adjustable for wall displays.

## Limitations

Worth stating plainly:

- The station network is **fictional**. Nothing here connects to real hardware,
  and nothing dispatches a real engineer.
- Telemetry covers a rolling 24-hour window. Longer-baseline statistics — the
  7- and 30-day health trends — are reconstructed deterministically and are
  labelled as estimates. Drift *rates* are only reported when they clear a
  two-sigma significance test against the data actually retained; the headline
  drift figure is the directly measurable offset from peers.
- Failure risk is a deterministic score, not a trained model.
- Operator state lives in `localStorage`. There is no backend and no
  multi-user coordination.
